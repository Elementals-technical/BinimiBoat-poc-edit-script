# 03 — DeckPlane і розстановка меблів

## Ідея площини

Меблі з лодкою з'єднуються **через додаткову площину** — `DeckPlane`. Це не меш і не entity, а обчислюваний ресурс у store:

```js
{
  orientation: 'horizontal',
  origin: { x, y, z },          // центр, зсувається переднім відступом
  size:   { x, z }              // метри; корисна площа палуби
}
```

**Розмір площини залежить від розмірів човна:** її обчислює `RuleBuildDeckPlane` з `DeckLength`, `DeckWidth`, `FrontIndent` і габаритів забору. Змінилась лодка → перерахувалась площина → усе, що стоїть на ній, реагує. Меблі ставляться **в контексті розміру площини**: їхні `position {x, z}` — це координати відносно площини, а не абсолютні координати сцени.

Поточна формула — спрощена модель із заглушкою `fenceInset = 0.10 м` (TODO: калібрування під реальну геометрію Deck+Fence).

## Склад меблів: декларативний FurnitureLayout

Джерело правди про те, ЩО стоїть на палубі — масив у конфіг-документі:

```js
FurnitureLayout: [
  { id: 'fl-corner3232-1', type: 'Corner3232', position: {x, z},
    rotationY: 0, color: 'Beige', size: 36, positionMode: 'auto' },
  ...
]
```

Масив шлеться завжди **цілим** (заміна top-level ключа). Стабільні `id` генеруються один раз. Крок reconcile порівнює бажаний склад із фактичними інстансами і сам створює/видаляє/оновлює entity (клон прихованого шаблону з іменем типу). UI ніколи не створює entity напряму.

## Етап 1 (зараз): фіксовані початкові позиції

**Поточний стан: меблі не розставлені.** Механіка (reconcile, клони шаблонів, кламп) готова, але реальних позицій немає.

План: початкові позиції **фіксовані**, задаються таблицями, які надасть **ROMA**. Очікуваний патерн інтеграції — той самий, що вже застосований для параметрики лодки: таблиця → згенерований `positions.json` (або розширення `layout-data.mjs` → `layouts.json`) → правило читає дані, не містить їх. Фіксовані позиції задаються в координатах DeckPlane, тому коректно поводяться при зміні розмірів лодки (кламп у межі робить `RuleClampFurniture`).

Те, що зараз у `RuleFurnitureLayout` (потокова розкладка «один за одним» уздовж Z) — **тимчасова заглушка** до отримання таблиць. Захардкоджені footprints меблів у `layout/layout-data.mjs` теж потребують калібрування за реальними мешами.

Відкриті питання до ROMA / клієнта:
- формат таблиці позицій (чи залежить набір/позиції від розмірів лодки?);
- чи існує поняття «пакет комплектації» (преднабори меблів);
- габарити (footprints) кожного типу меблів або дозвіл зняти їх з мешів.

## Етап 2 (майбутнє): drag-and-drop

Передбачено з самого початку — нові фічі мають це враховувати:

- `positionMode: 'auto' | 'manual'` на кожному елементі layout. Drag переводить елемент у `manual` — автоматична розкладка його більше не чіпає, фіксована позиція залишається тільки початковою.
- Каркас модуля вже є: `modules/drag-movement/` (DragMovementModule + DragPlaneCalculator + MovementController). Сесія drag: pointerDown → фіксація площини з DeckPlane → move: проєкція на площину + кламп + колізії → up: запис позиції у стан **через штатний `setConfiguration`** (не напряму в entity).
- TODO в каркасі: реальний raycast у `_pick`, AABB-колізії меблі↔меблі, touch-input.
- Специфікація: `docs/drag-and-droup.md` (layers, merge, transition — далекий приціл).

Правило для всіх майбутніх змін: **позиція меблів — частина конфігурації**, а не стан сцени. Drag — це лише зручний спосіб згенерувати патч.
